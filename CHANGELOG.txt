Solix changelog
===============

0.3.7+fabric (2026-11-08)
First Fabric 1.20.1 release (branch fabric-1.20.1). Same light engine as Forge 0.3.7; only the loader layer differs.
- Fabric Loader 0.14.21+ on Minecraft 1.20.1, no Fabric API needed. Mod id solix; it also provides the id "starlight",
  so Fabric mods with Starlight support turn it on: Bobby (light of its cached fake chunks, through its mixin on
  StarLightInterface$1/$2) and C2ME's fast chunk serializer (writes Starlight's light format). A real Starlight jar is
  refused by Fabric Loader (duplicate id); ScalableLux and Phosphor are declared as breaking, as is Sinytra Connector
  (use the Forge jar there).
- Porting Lib positional light emission: blocks overriding LightEmissiveBlock#getLightEmission(state, level, pos)
  (Forge's positional emission ported to Fabric, used by Forge ports such as Create Fabric) are handled like Forge's
  positional emission: real emission at the position, no cached fast path, the 0.3.6 light view and the 0.3.7
  ClassCastException fallback. Porting Lib only hooks it into the vanilla light engine, which Solix replaces. Without
  Porting Lib every block uses its per-state emission (vanilla behaviour).
- The 0.3.6 light view (safe_light_view) is kept: vanilla getLightBlock/getFaceOcclusionShape of dynamic-shape blocks
  are positional too, and off-thread ServerChunkCache#getChunk waits on the server thread on Fabric as well. Its
  block entity lookup reads the chunk's block entity map directly (Forge: getExistingBlockEntity, same map).
- config/solix.toml in Fabric's config folder, same keys and defaults.
- Debug properties: -Dsolix.debug.sectionTypes and -Dsolix.debug.positionalEmission log once the levels are loaded.
- Access widener instead of the access transformer. The Forge AT's two ChunkHolder entries (f_140018_, f_142982_) are
  inherited from Starlight Forge and unused, so they have no counterpart.
- Compatibility scan of the SolPack Fabric instances (208 jars): Sodium (Inject at RETURN of applyLightData and
  handleForgetLevelChunk, kept by Solix's client mixin), C2ME 0.2.0+alpha.11 (threading-lighting hooks a
  tryScheduleUpdate lambda Solix does not overwrite; serializer resolves SWMRNibbleArray/SaveState/ExtendedChunk by
  name, all kept), ModernFix, Lithium, VMP, Fabric API, Architectury, Cardinal Components: no conflicting target. No
  scanned mod puts a version condition on "starlight".

0.3.7 (2026-11-04)
Fixes from a full audit after the Age of Fate #149 deadlock (0.3.6).
- A chunk's light ticket is now released even when lighting that chunk throws (a mod's light callback, for example).
  Before, the ticket was only released on success, so a failure kept the chunk loaded and could make server stop wait
  for it. The chunk stays marked as not lit and is relit on its next load.
- 0.3.6's light view no longer calls LevelChunk#getBlockEntity, which promotes pending block entities (registering a
  ticker with the level) and drops removed ones from the chunk's map, both only allowed on the server thread. It uses
  Forge's existing-block-entity lookup and ignores removed block entities.
- A block whose light code casts the BlockGetter it gets to Level (or ServerLevel/LevelReader) used to fail with a
  ClassCastException on the light thread and lose that chunk's light update. The first failure per block class is now
  logged and that class is given the real level from then on, like before 0.3.6; every other block keeps the safe view.
- config/solix.toml: new safe_light_view = true (added to existing files on start). false hands every mod the real
  level, as in 0.3.5.
- If the light worker threads cannot be started (for example no native thread can be created), Solix switches to
  serial lighting. Before, every scheduling pass failed again, the light work stayed queued and server stop waited for it.
- Queuing light work now also asks for a scheduling pass (vanilla only did that while polling server tasks, which a
  server that is permanently behind schedule skips). The throttle still applies.
- Memory: finding a chunk's light sources no longer creates a list with one BlockPos per source, the sources are
  queued while the chunk is scanned (same order, same light).

0.3.6 (2026-11-04)
Fix for Age of Fate #149 / Solix #2 (world load hangs for good with Ender IO machines, single player and dedicated server).
- Server: mods' position-aware light callbacks (getLightEmission, getLightBlock, getFaceOcclusionShape) now get a
  light-only view of the world instead of the ServerLevel. They run on a light worker thread (a Solix worker, or a
  vanilla worker when lighting is serial: parallelism 1, which is the default below 8 CPU threads). Ender IO's machine
  blocks read their own block entity from getLightEmission (Forge's getExistingBlockEntity, which it uses because the
  mod id "starlight" is not loaded); on the real level that call queues the lookup on the server thread and waits for
  it. When the server thread was itself waiting for a chunk whose light that worker was computing (getChunkBlocking),
  neither could continue and the server stopped with the 180 s watchdog. The view reads the chunks the light engine
  uses (never loads one, never waits for the server thread); a chunk that is not there reads as air without block
  entity. It also removes a round trip to the server thread for every such callback.
- The client light engine and fake/virtual levels are unchanged (they keep getting their own level).
- Not Solix: ImprovableSkills' Accelerated Furnace skill calls Level#getBlockEntity on chunks that may not be loaded
  from the player tick, which is what puts the server thread into getChunkBlocking in the dedicated server reports.

0.3.5 (2026-11-01)
- Dedicated server: checking whether a block's light emission depends on its position no longer loads client-only
  classes. Class#getMethod resolved every public method signature of the block class, so blocks with a client type
  in any of them (MineColonies' town hall: ClientLevel) logged a RuntimeDistCleaner error the first time one was
  placed and were treated as position-aware (slower light path). The method is now resolved like the JVM links a
  call, which only loads its own parameter types; same result as before on the client. Also covers block classes
  whose signatures name a class from a missing optional mod.

0.3.4 (2026-10-17)
Fixes from a second code audit.
- Serial lighting (parallel = false, parallelism = 1, or few CPU cores): server stopping/world close now also waits
  for the light update being processed (0.3.2 only covered parallel workers).
- Parallel scheduler: a light task can no longer be left unfinished. If handing a chunk to a worker fails (e.g. no
  new thread could be created) the work stays queued (logged once); if a worker's error handling itself fails, its
  task is still marked done. Before, either case kept "light work pending" set forever, so server stop waited
  forever. A failure after a chunk's light work was already done no longer queues that work a second time.
- Client: when the server re-sends a chunk the client already has, and the packet has no light at all for a layer
  (e.g. an all-air chunk), the chunk's old light for that layer is replaced by empty light instead of kept.
- Reverted 0.3.2's C2ME light version change. C2ME's fast chunk serializer also saves the light sections just below
  and above the world incorrectly; with its version 8 Solix relights those chunks on load and repairs them, with
  version 9 the broken sections were kept. Only relevant with C2ME's gcFreeChunkSerializer, which RatPack keeps off.
- Targeted darkening: a block reporting more light blocking than 15 (possible with mods) no longer overflows into
  the neighbouring field of the queue entry.
- config/solix.toml:
  - a file that is not valid UTF-8 (e.g. an accented comment saved by an ANSI editor) no longer drops every setting
    back to its default;
  - a UTF-8 byte order mark, quoted keys and single-quoted values are understood, and a # inside a quoted value is
    kept;
  - if adding the propagation setting to an existing file fails (read-only file), the warning says so; the other
    settings were read and are used (the old message claimed defaults were used);
  - the added block uses the file's own line endings;
  - parallelism above the number of CPU threads is lowered to it (huge values would start that many threads).
- mods.toml now only accepts Minecraft 1.20.1 and Forge 47 (it accepted 1.20.2-1.20.6 and Forge 48+, where Solix
  would crash).
- Removed dead code (commented out): ExtendedAbstractBlockState#isPositionAwareEmission and its per-block-state field
  (nothing read them), an unused 4 KB array in every sky light engine, unused imports. Public Starlight API that
  Solix itself does not call (relightChunks, loadInChunk, removeChunkTasks, edge check queueing) is kept on purpose.
- Fixed the queue entry layout comment (13 unused bits, 5 flag bits).

0.3.3 (2026-10-12)
- Parallel scheduler: the main thread's "is there light work?" check (run for every task it polls) no longer takes
  the light queue lock, and a scheduling pass only holds that lock to copy the queued chunk keys instead of for the
  whole pass. Less main thread waiting during chunk generation and pre-generation.
- The server always sends the light of sections that contain a changed block again. Since 0.3.0 sections whose
  light ended up unchanged are not sent; before that, the changed block's section was always re-sent, which also
  corrected a client whose own light calculation for the change differed (e.g. at the edge of its view distance).
  Unchanged sections elsewhere are still not sent.
- Serial lighting (parallel = false, parallelism = 1, or few CPU cores): a light update that throws no longer stops
  that dimension's light updates for good (vanilla only re-arms its light scheduling after a successful run) and no
  longer keeps the chunk loaded; the chunk's updates are retried once and then dropped and logged, like the parallel
  path since 0.3.2.
- Light readers and light engines now make the same client/server decision, so mod levels that are neither a
  server level nor client side (some fake or virtual levels) are lit instead of silently ignored.
- A pure client no longer initialises the parallel scheduler (it only logged a misleading "worker threads" line).
- Memory: the per-thread pool of spare light arrays is capped at 128 (256 KB), and light queues grown by one huge
  update are shrunk back afterwards instead of being kept for the world's lifetime.
- Client: a chunk packet replaces light cached from earlier light-only packets for that chunk, so sections the
  packet leaves out cannot keep stale data. Light from packets is no longer copied twice (2 KB per section).
- Chunk lighting: the light source scan uses the block state's emission field for blocks without position-dependent
  emission instead of Forge's positional call for every block of a candidate section.

0.3.2 (2026-10-12)
Fixes from a full code audit.
- getDebugSectionType no longer reports light data (LIGHT_AND_DATA) for sections whose data getDataLayerData does
  not return: hidden block light sections, and sky light of chunks that are not lit yet. A mod trusting the type
  (e.g. Voxy-style ingest) could get null data.
- Server stop and world close now wait for light updates that a parallel light worker has started but not
  finished. Before, vanilla's "any work left?" check only saw the queue, so a save could catch an update halfway.
- If a parallel light worker fails, its chunk's light updates are retried once (merged into newer work for the
  chunk) instead of being dropped; if the retry fails too they are dropped and logged, as before.
- A light worker finishes its chunk before asking for the next scheduling pass, so work queued for that chunk in
  the meantime is not skipped until the next pass.
- C2ME's fast chunk serializer (ioSystem.gcFreeChunkSerializer, off in RatPack) wrote light version 8, which Solix
  treats as outdated, so every chunk it saved was relit on load. It now writes Solix's version (same data format).
- Client: chunks the server tells the client to forget are also removed from the "light enabled" set (it only grew
  until the world was closed).
- World generation: brightness queries outside the generation region return 0 instead of throwing.
- Fake or virtual levels without a chunk source, and light engines created without a chunk getter, no longer
  cause a NullPointerException.
- mods.toml credits FlowSched to ishland (per its licence).

0.3.1 (2026-10-10)
- Faster light section bookkeeping: deciding which light sections must exist around a chunk checked up to 27
  neighbouring sections one by one for every light section of 9 chunks. It now builds one bitmask of non-empty
  sections per chunk column and answers each check with a few bit operations. This ran for every chunk lit on the
  server (5-10% of light worker time in profiles, no longer visible after the change) and on the client's render
  thread for every chunk received. Same decisions as before (checked against the old search for every call in a
  test build; saved light identical to 0.2.2/0.3.0); worlds with more than 63 light sections keep the old check.
- Evaluated and not adopted: Vector API / FFM (Minecraft 1.20.1 runs on Java 17, where the Vector API needs extra
  launch flags and FFM does not exist; the light loop is a sparse search bound by block reads); @Stable and
  block-state-id emission tables (opacity and emission are already single field reads, KubeJS changes emission at
  runtime); delaying or batching light packets (already sent once per tick per chunk, unchanged sections are no
  longer sent since 0.3.0, a custom channel would break vanilla clients and mods reading light packets);
  snapshot-and-commit worker threads (light spills across chunk borders, overlapping writes would be lost; workers
  are mostly idle); heightmap gating (block light never travels more than 15 blocks and sky setup already stops at
  the first opaque block). Rendering techniques (multi-draw indirect, ray-traced GI, shadow maps) belong to the
  renderer and shader mods, not the light engine.

0.3.0 (2026-10-08)
(+0.1.0: this change adds/removes more than 500 lines, mostly the reworked light queues and decrease.)
- Brightest-first light queues (Dial's algorithm): the increase and decrease queues are split into 16 buckets by
  light level and processed from 15 down. A block is now lit once at its final level, instead of being lit by a
  weaker source first and overwritten by a stronger one (mixed-level sources in chunk lighting, re-lighting after
  a block change).
- Targeted darkness: when light is removed or blocked, Starlight darkened every block whose level could have come
  from the changed block and then re-lit the whole area from its border. Placing a block in a lit room did this
  for the entire region behind it, although almost every block there is also lit along another path of the same
  length. Such blocks are now only queued as candidates and darkened when neither their own emission nor any
  face-open neighbour still provides their level. The source of a block's light is not stored anywhere (no extra
  memory, no save format change); it follows from the light values themselves.
  Below a removed light source (a changed block without a brighter neighbour, or a removed sky column) nearly
  everything loses its light, so the classic darkening is kept there; the checks would only cost time.
- Sections whose light ends up byte-identical after an update (darkened and re-lit within the same update) are no
  longer reported as changed. The server then skips the light packet and the chunk's unsaved mark for them, and
  clients skip re-meshing those sections and their neighbours.
- A source block's light is never lowered when it is restored after a decrease if a brighter neighbour has
  already lit it.
- Queued light work left behind by an update that threw is cleared, so a pooled light engine cannot replay it.
- New config key in config/solix.toml: propagation = targeted (default) | ordered | classic.
  ordered = brightest-first queues only, classic = Starlight's original FIFO propagation (fallback if you suspect
  a lighting bug). It is added with its documentation to existing config files on first start.
- Debug: -Dsolix.debug.lightStats=true logs light engine counters every 10 s, separately for server and client
  (update counts and times, queue pops, candidates kept/darkened, light writes, sections reported/unchanged).
- Tested on a dedicated server with C2ME + ModernFix (1 and 4 light workers): saved light after relighting a world
  and applying block edits is identical to 0.2.2 in every mode. Single stone blocks placed/removed in a lit room:
  14-20% less light time, 47% fewer light writes than classic; big /fill and glowstone add/remove batches do the
  same work as classic (ordered: 6-9% fewer writes). Depending on the edits, 10-40% of the sections an update
  touched ended unchanged and are no longer re-sent to clients.
- Not adopted, after evaluation: storing a per-block pointer to the brightest neighbour (needs ~1.5-2 KB more per
  light section and layer, is not in the save format, and goes stale whenever light is loaded or received instead
  of propagated; the targeted darkness above gets the same benefit without it); spreading darkness over several
  ticks (server light already runs off the main thread, and a half-finished decrease leaves inconsistent light
  that later updates and saves would pick up); SWAR-packed nibble arithmetic (light updates touch a sparse set of
  blocks, so dense 16-lane passes do more work, and Forge's positional opacity and face shapes cannot be packed).

0.2.2 (2026-10-02)
- Parallel scheduler priority by distance (idea from Lucis): each chunk's light task gets the chunk's vanilla queue
  level (ChunkMap#getChunkQueueLevel, lower = closer to a player / higher ticket) as its FlowSched priority instead
  of ScalableLux's constant, so chunks near players light first. One FlowSched priority bucket per vanilla level.

0.2.1 (2026-10-02)
- Jar now contains LICENSE-FlowSched.txt (the MIT notice for the vendored FlowSched executor); 0.2.0 missed it.

0.2.0 (2026-10-02)
(+0.1.0: this change adds more than 500 lines, mostly the vendored FlowSched executor.)
- Parallel server light scheduler from ScalableLux (patch 0006): each chunk with queued light work becomes a task on
  a pool of "Solix Light Worker" threads that locks the 5x5 chunks around it, so independent areas light in
  parallel. Includes ScalableLux 0db04dc (finished per-chunk futures are removed; they leaked before).
  The client keeps Starlight's synchronous path.
- Vendored only FlowSched's executor (ExecutorManager, WorkerThread, Task, LockToken, SimpleTask,
  BucketTaskPriorityQueue, Assertions; MIT, commit a60f952, which includes the 42e2aad relock deadlock fix) under
  ca.spottedleaf.starlight.interndep.flowsched. LICENSE-FlowSched.txt is in the jar.
- tryScheduleUpdate throttle (ScalableLux 9d6f8cb) as a @Redirect of hasLightWork(): a scheduling pass runs when new
  light work was queued, otherwise at most every throttle_ms. Needed because C2ME's threading.lighting calls
  tryScheduleUpdate after every light-thread task.
- New config file config/solix.toml (created on first start, read once at mixin load):
  parallel = true, parallelism = 0 (0 = automatic, max(1, CPU threads / 4)), throttle_ms = 10.
  parallelism = 1 or parallel = false uses the serial Starlight path (fallback for ScalableLux issue #36).
- If Starlight, ScalableLux or Lucis is installed, Solix disables its own mixins and logs why, so Forge's
  incompatibility error is shown instead of a mixin crash.
- A worker task that throws now logs the chunk and still completes the chunk's light future (no stuck ticket).
- Debug: -Dsolix.debug.sectionTypes=true logs getDebugSectionType counts around spawn at server start.

0.1.4 (2026-10-02)
- LevelLightEngine.getDebugSectionType now reports LIGHT_AND_DATA for sections with light data (from ScalableLux
  77b85a8). Starlight nulls vanilla's light engines, so this always returned EMPTY and Neo-Voxy skipped every chunk
  in its ingest. Out-of-range section Y returns EMPTY instead of throwing.
- setLightEnabled/lightOnInSection are implemented (from ScalableLux 1f1f5cf): the client's LevelRenderer only
  rebuilds dirty sections where lightOnInSection is true. The set is synchronized.

0.1.3 (2026-10-02)
- Position-aware emission: also accept Quark's own Zeta forwarding override (org.violetmoon.* classes), not only
  Zeta's. With Quark + Zeta + Mekanism + Modular Routers loaded, 0.1.2 flagged 199 blocks; the extra ones were
  Quark blocks whose getLightEmission only forwards to the default getLightEmissionZeta.

0.1.2 (2026-10-02)
- Forge-correct opacity cache. Starlight Forge 1.1.2 computed the cached light opacity and then always overwrote it
  with -1, so every light step took the slow path. The cached value is now kept (vanilla's cache.lightBlock) except
  for block states with a dynamic shape, conditionally full-opaque states, and blocks with position-aware light
  emission. The field starts at -1, so states whose cache ModernFix has not built yet use the slow path.
- Position-aware emission detection (idea from ScalableLux's NeoForge port): a block class counts as position-aware
  when it overrides Forge's IForgeBlock#getLightEmission(BlockState, BlockGetter, BlockPos) (cached per class).
  Zeta's forwarding override is ignored when getLightEmissionZeta is still the interface default. Forge's own
  BlockPos.ZERO probe is not used, because some mods (e.g. Mekanism fluid tanks, Modular Routers camouflage) return
  0 there.
- isConditionallyFullOpaque is now read from the block state's final fields instead of a value cached in initCache,
  so it is also correct before ModernFix builds a state's cache lazily.
- Block light sources: sections whose palette has no state that can emit light are skipped instead of scanning all
  4096 blocks (sections containing position-aware blocks are still scanned).
- Debug: -Dsolix.debug.positionalEmission=true logs every block with position-aware emission at load complete.

0.1.1 (2026-10-02)
- Backported Starlight forge-branch fixes made after 1.1.2 (all apply to 1.20.1 unchanged except where noted):
  - 6585522: light queue methods return the per-chunk task object, so many block updates in one chunk in the same
    tick add the chunk-work ticket only once (water draining etc.). Needed by the parallel scheduler.
  - 2084f46: do not fill/maintain vanilla's unused skyLightSources (saves time on chunk creation and block changes).
  - 2b3204b: default ExtendedWorld implementation in Level, for mods with custom Level classes.
    Fixed an upstream typo in it: getAnyChunkImmediately used (chunkX, chunkX) instead of (chunkX, chunkZ).
  - 4d59d86: initialise the nibble arrays in the ChunkAccess constructor, for mods with custom ChunkAccess classes.
  - c4d051c: WorldGenRegion returns brightness 0 until the target chunk is lit (vanilla-like feature placement,
    e.g. mushrooms in swamps).

0.1.0 (2026-10-02)
- First version. Based on Starlight Forge 1.1.2 (PaperMC/Starlight forge branch, commit 1cda73c), built for
  Minecraft 1.20.1 / Forge 47.4.16.
- Rebranded to mod id "solix" (display name "Solix"); Java packages stay ca.spottedleaf.starlight so C2ME's
  Starlight light-format support keeps working. The saved light format (starlight.light_version etc.) is unchanged,
  so worlds can be moved between Starlight 1.1.2 and Solix.
- Declares Starlight, ScalableLux and Lucis as incompatible (Forge refuses to load with them installed).
- C2ME gc-free chunk serializer: report "starlight" as loaded so it keeps writing Starlight light data.
- Fix: relightChunks sent light-update notifications for SectionPos(chunkX, y, chunkX) instead of chunkZ
  (from ScalableLux c034543).
